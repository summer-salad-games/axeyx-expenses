# Small Business Transaction Register

Status: revised scope approved by the owner on 2026-11-15: expenses and revenues, no notifications/realtime, clean development database without backward compatibility. Owner-approved architecture and authoritative functional specification (2026-11-11). Milestones 1–6 are implemented and verified locally, including backup/recovery and security hardening. Production deployment and release checks remain pending in PLAN.md.

## 1. Scope

Self-hosted transaction register for one company and at most 20 fixed users, with shared visibility of expenses and revenues and desktop/mobile HTTPS access. One Laravel/Filament/Livewire application; SQLite alone; native Linux on Raspberry Pi 5 ARM64 with SSD. Existing Caddy, CrowdSec and static sites must survive unchanged except explicitly reviewed additive integration.

Excluded: registration, invitations, user-management UI, multi-company/tenancy, invoicing, banking, payments, reimbursements, approval workflows, budgets, ERP/accounting, CSV export, native apps, public APIs, external identity providers, complex RBAC/analytics/cache infrastructure, containers, Kubernetes, Redis service, separate frontend, ordinary transaction email, client-side backup encryption, persistent local backup archives.

## 3. Schema and integrity

All IDs are server-assigned. Required foreign keys restrict parent deletion unless stated otherwise. No account hard-deletion interface. Administrators may permanently delete categories only when no transaction references them; otherwise disable them. Use indexes justified by 20-user queries, not speculative scale.

| Table | Columns and constraints | Indexes/notes |
| --- | --- | --- |
| users | id; name <=120; normalized email unique <=254; password hash; role CHECK administrator/editor/viewer; is_active default true; must_change_password boolean default true; onboarding_completed_at nullable timestamp; remember_token; auth_version integer default 1; app_authentication_secret nullable TEXT; app_authentication_recovery_codes nullable TEXT; created_at/updated_at | Framework-compatible MFA fields use maintained encryption/casts; never serialize secrets. auth_version revokes old file sessions on disable/password reset/MFA reset/role change. Password/completion onboarding state is server-owned. |
| categories | id; type expense/revenue; name <=100; protected Unicode NFC/casefolded name_key; is_active default true; created_at/updated_at | Names trimmed, unique by (type, name_key); immutable type; disable preserves history. |
| transactions | id; transaction_date DATE; type CHECK expense/revenue; amount_millimes INTEGER CHECK typeof integer and >0 and <=999999999999; category_id FK; description nullable plain text <=5000; created_by FK users; created_at/updated_at | Index transaction_date, (type, transaction_date), (category_id, transaction_date), (created_by, transaction_date); composite category/type FK prevents mismatches. Creator immutable. Currency is constant TND, not an editable field. |
| attachments | id; transaction_id FK; path unique; original_name <=255; mime_type; size_bytes positive integer; sha256; uploaded_by FK users; created_at/updated_at | Index transaction_id. Server-generated relative path on a fixed private disk; immutable bytes after creation. Original name is display metadata only. |
| audit_logs | id; actor_id nullable FK users; actor_kind (user/operator/system); action; subject_type/id; minimal metadata JSON; created_at | No financial descriptions, attachment contents or authentication secrets. CLI actions record local operator context, affected user and timestamp. Runtime offers no edit/delete UI. |
| migrations | Standard Laravel migration history | No sessions/cache tables: these use files. |

Amount ceiling is 999999999,999 TND to bound inputs safely; document as configurable within signed 64-bit constraints. Accept ASCII digits with at most one decimal comma or point and one to three fractional digits when a separator is present; whole-number inputs are valid. Parse exactly into integer millimes, padding missing fractional places without rounding. Reject mixed/repeated separators, digit grouping, signs, exponents, zero, negatives, excessive precision, non-finite values and overflow. Display French decimal commas, exactly three fractional digits and TND: inputs 12,5 and 12.5 both display as 12,500 TND. Store positive integer magnitudes with an expense/revenue type. Individual transaction amounts display expenses with − and revenues with +. Dashboard direction totals remain positive under explicit Dépenses/Recettes labels; period net may be negative and is not a bank balance. Aggregate each direction separately with integer SUM/COUNT; never SQLite TOTAL or floating decimal casts. Guard aggregate overflow instead of silently coercing. Charts carry millimes and format labels exactly.

## 4. Authentication and CLI accounts

Laravel Argon2id password hashing, sessions, CSRF, regenerated login sessions, complete logout/invalidation, rate-limited password and MFA challenges. Require passwords of at least 12 characters; allow passphrases, spaces and Unicode, without mandatory uppercase/lowercase, numbers or symbols; reject a local blocklist of at least 3,000 common passwords matching the minimum length, without a network lookup; hidden interactive entry/confirmation for CLI passwords. No secrets in command arguments, history, logs or fixture commits. Production cookies Secure/HttpOnly/SameSite=Lax, host-only; inactivity timeout 120 minutes, no persistent remember-me UI.

Page GET/HEAD requests retaining a Livewire update header after an HTTP redirect must render as ordinary pages. Component updates remain POST requests with transport-header, JSON, CSRF and persistent authorization checks intact.

Use Filament required app-based TOTP and recovery codes. Users without enrollment can reach only MFA setup and logout. Sensitive profile changes require password/second-factor confirmation; users cannot disable required MFA and continue using the panel. Recovery codes are single-use; verify replay/concurrent use prevention with the file cache's atomic locks. Administrators reset enrollment through CLI; next login requires enrollment. No email-based MFA, email password-reset flow or email address changes through the profile. Account security provides password change and MFA/recovery management only.

First-login onboarding is mandatory and visually separate from the application: `/setup/mfa` enrolls MFA, `/setup/password` chooses and confirms a strong password different from the temporary one while confirming current credentials, and `/setup/complete` displays “Tout est prêt” with an explicit application-entry button. `/setup` redirects to the first unfinished step, or the dashboard when complete. Initial MFA enrollment verifies the authenticator code without repeating the temporary password; later enrollment after an MFA reset retains password confirmation, including when password selection is still pending. Code validation, attempt limits and replay prevention remain mandatory. All steps share a centered setup card and a three-icon progress indicator (MFA shield, password key, completion rocket). Show only branding and CSRF-protected sign-out, without profile menu or app navigation. Keep OTP autofill styling neutral and provide an explicit username hint for password managers where a password field is present.

Persist completed steps across sign-out/sign-in; resume the first unfinished step after normal authentication/MFA. App data stays inaccessible until MFA, password choice and final confirmation are complete. Only a successful user password change clears its requirement, atomically with audit/session revocation; the confirmed browser stays authenticated. Final confirmation stamps `onboarding_completed_at` and audits idempotently. Existing fully configured accounts are backfilled as complete; pending accounts remain pending. CLI password resets set a temporary password and clear final completion. MFA reset clears MFA and final completion while preserving an already chosen password. No new account configuration fields are part of the rocket step.

All command-line tools and scripts use English for help, prompts, status, errors and validation. The web interface remains French; console execution must restore the previous locale when returning.

Account commands (implemented in milestone 2):

| Command | Behavior |
| --- | --- |
| php artisan accounts:create | Prompt name/email/role and hidden temporary password twice; default viewer; require MFA and user-chosen password; audit. |
| php artisan accounts:list | Show ID, name, email, role, active status and enrollment status only. |
| php artisan accounts:role USER ROLE | Validate one of the three roles; audit and revoke old sessions. |
| php artisan accounts:disable USER | Set inactive, rotate remember token/auth_version, revoke sessions; audit. |
| php artisan accounts:password USER | Hidden temporary password prompt/confirmation, hash, require user-chosen replacement after next MFA login, revoke old sessions; audit. |
| php artisan accounts:mfa-reset USER | Explicit interactive confirmation; clear enrollment/recovery state, revoke sessions; audit. |

USER is a stable ID or email, never a password. No public registration, invitations or user-management resource. No account hard deletion. No CLI command accepts a plaintext password option. Account disabling and credential/role resets revoke existing sessions; authorization is rechecked on every HTTP/Livewire/download request.

## 7. Attachment security and consistency

- JPEG (.jpg/.jpeg), PNG (.png), WebP (.webp), PDF (.pdf) only. Validate extension and independently detected content/MIME; verify image readability and PDF signature in addition to maintained file validation. Reject SVG/HTML/scripts, spoofed formats, invalid/malformed files, forged stored-file references and any client-supplied path. Do not claim signature checks constitute malware scanning.
- Defaults configurable: 10 files/transaction, 10 MiB/file, 50 MiB combined (existing retained files + new files). Enforce server-side under concurrent edits. Align Livewire temporary limits, PHP upload/post limits and Caddy body limits; use individual uploads to avoid a 100 MiB simultaneous request. Enforce limits again when finalizing.
- Private temporary uploads and final Laravel filesystem disk outside public/. Generated names/paths; no public symlink or original filename as a storage key. Exclude upload directories from execution. Rate-limit uploads; expire abandoned temporary files.
- Authenticated route loads attachment by ID, resolves its stored transaction, checks policy and permitted path prefix, and streams with fixed allowlisted Content-Type, nosniff, private/no-store and safely encoded Content-Disposition. Do not show image previews in the upload field. Saved images may show safe thumbnails. Every saved attachment, image or PDF, has the same Ouvrir action at /attachments/{id}/view with inline disposition and a restrictive sandbox policy; Télécharger remains a separate attachment-disposition action. There is no separate /preview route. Original filenames are escaped and stripped of control characters. No response accepts a user path.
- Stage files privately, validate all limits, then persist transaction/attachment/audit rows in a short transaction with bounded lock retry. Filesystem and DB are not atomically committed: compensate failed commits, remove files only after successful record removal, and use retryable cleanup plus a conservative reconciliation command to recover from crashes. Never delete files while any attachment record references them; reconcile stale unreferenced generated files only after a grace period. Audit add/remove actions.
- Use one file-backed application consistency lock for attachment mutations and backup snapshot/staging; release it before network transfer. Serialize aggregate-limit checks and deletion cleanup; no long database transaction around copying or network. Reconcile after interrupted uploads/deletes. Permanent transaction deletion uses this same lock, removes transaction/attachment rows and writes audits in one short transaction, then removes unreferenced files after commit. Keep files if the transaction fails; retry failed filesystem cleanup.

File sessions/cache are private. No network filesystems. Dashboard reads use a short DEFERRED snapshot transaction and never the storage consistency lock. Short write transactions, bounded retries only for known transient busy errors and idempotent operations; report safe errors when retries exhaust. ## 10. Google Drive backup and recovery

Google Drive is the sole persistent backup destination. Owner-confirmed daily systemd timer: 03:15 Europe/Luxembourg, Persistent=true to catch a missed run, one attempt at a time with flock and bounded service/network timeouts. Owner-confirmed retention: latest 30 successful backups, always retaining at least the last verified good backup. No rclone crypt or additional encryption.

Backup algorithm:

1. Create an attempt ID and restrictive (0700 directory/0600 files) temporary staging area on private SSD with enough free space. Track only non-secret attempt status outside the archive. Acquire the storage consistency lock; attachment writes/removals wait while authorized reads continue.
2. Use SQLite online backup API (PHP SQLite3::backup or sqlite3 .backup), never cp of the live DB/WAL. Run integrity_check and foreign_key_check against the snapshot. Copy exactly the immutable attachments referenced by that snapshot, including every referenced attachment, verify each stored size/hash. Fail if anything is missing. Release the lock immediately after local staging; no network under it. Avoid long DB write transactions.
3. Package snapshot, referenced files, a whitelist of non-secret recovery settings/schema/app release information and a manifest with hashes/counts. Exclude .env, APP_KEY, rclone credentials, source secrets, cache/session files, logs and temporary uploads. After staging and releasing the consistency lock, sanitize only the snapshot: clear MFA secrets/recovery codes/remember tokens, replace every password hash with a separately generated discarded random credential, require fresh onboarding, and VACUUM the copy so removed authentication data does not remain in free pages. The live database remains untouched. Archive one full unencrypted .tar.gz containing database.sqlite, referenced attachments and manifest.json; include an external manifest and publish a completion marker only after verified upload. Financial data remains sensitive.
4. Upload into an attempt-specific directory under the dedicated Drive folder using rclone copy (not a broad sync). Check archive/manifest sizes and hashes with rclone check; require checksums or downloaded verification, never accept size-only silently. Publish and read back a completion marker only after verification. Incomplete uploads are never restore candidates.
5. Apply retention only inside this app's remote folder after a verified backup. Remove old completed attempts beyond policy while preserving the newest verified good one; prune stale incomplete attempts separately. A retention error fails the attempt and is recorded in local status and systemd journal. Test Google Drive trash/purge semantics and quota reclamation before selecting narrowly scoped permanent deletion flags; never purge the whole Drive or empty account-wide trash.
6. Clean local archive/snapshot/attachment staging on success or failure. Shell/PHP cleanup handles normal errors/signals; systemd ExecStopPost and next-start/boot orphan cleanup handle killed processes. Persist no local backup archives. A crash/power loss can leave temporary data until the next cleanup; identify and remove only this service's abandoned staging paths.
7. Record each attempt ID, UTC start/end, short stage and success/failure in private local metadata and expose a CLI status command. Systemd journal records a sanitized outcome. Record interrupted attempts at ExecStopPost/next start and clean abandoned staging safely. No SMTP, email helper, alert outbox or alert-retry timer. The owner checks backup status manually; do not claim proactive failure notification. Expected recovery point objective: up to 24 hours plus failures; restore time is measured in rehearsal.

Use a dedicated Google account/folder where feasible, minimum rclone Drive scope that can create/manage/read these backups (evaluate drive.file), no sharing/public links and protected OAuth tokens. Folder selection alone is not an OAuth authorization boundary. Keep credentials and OAuth recovery material in a separate owner-managed secure recovery store; the owner approved one standard restore path on 2026-11-15: every restore creates a fresh APP_KEY and resets all account passwords and MFA, so the old key is not a backup recovery dependency. Unencrypted Drive backups expose financial data and attachments if that account is compromised. Home-network/power/SSD/Google outages remain operational risks.

Recovery: select a completed verified attempt; download into an isolated environment; verify manifest/archive hashes before extraction and reject unsafe paths; integrity/FK-check DB and match attachment hashes/references; restore to private paths with correct owner/modes; restore separately held service credentials and non-secret config; generate and privately persist a fresh APP_KEY and clear previous decryption keys; discard stale sessions under a documented procedure; migrate only to a compatible tested release; test MFA/roles/attachments/stats; then owner performs controlled production cutover/service restart. Never reset production. Rehearse before launch and at least quarterly; tests use fake/isolated destinations, never production Drive.

Standard owner-approved restore procedure (2026-11-15): always generate a new application key and clear all restored TOTP secrets/recovery-code data without attempting to decrypt it. Invalidate every restored password, rotate authentication versions/remember tokens and clear all sessions before reopening access. Provision a separate temporary password for each account through hidden operator CLI prompts; force MFA enrollment, a different user-chosen password and final onboarding confirmation. Keep account IDs, roles, active/disabled status, transaction ownership, categories and attachments unchanged; disabled accounts remain disabled. Do not use a shared temporary password or put passwords in arguments, logs or backups. Rehearse this mode on an isolated restore, including disabled accounts and denial of old passwords/recovery codes/sessions. Only authentication data is encrypted with APP_KEY in the current application; revisit keyless recovery before adding any encrypted business data. Restore uses private validated staging, explicit confirmation and an offline-writers acknowledgment. The operator stops only the app-specific PHP workers and other CLI writers; keep temporary rollback state until replacement verification succeeds. A crash journal supports recovery while maintenance remains active. Never reset current accounts except as part of an explicitly requested restore.
